# Plano de Ação — v1.17.0: Chat com Suporte Psicopedagógico (NAP) — RF15

**Data:** 2026-06-15
**Solicitado por:** Gabriel Malheiros de Castro
**Contexto:** Quarta versão da fase "robustez primeiro" e **último requisito funcional em aberto**
(B3/RF15). Diferente do chatbot (RF16, motor curado local já entregue na v1.11.0), este é um **canal de
mensageria humano** entre o aluno e o Núcleo de Apoio Psicopedagógico (NAP). Prioridade 🟢 baixa,
complexidade G — deixado por último entre as features justamente por isso.

## Objetivo

Implementar o **B3/RF15** — chat direto aluno↔NAP com troca de mensagens persistida. O schema Prisma
**já modela** as tabelas de suporte (`ChatTicket`/`ChatMensagem`), então o esforço concentra-se em
endpoints + UI + (opcionalmente) tempo real.

## Etapas

### Decisão de arquitetura (antes de implementar)
- [ ] 1. Definir transporte: **(a)** polling HTTP simples (mais simples, sem nova dependência) ou
      **(b)** Socket.io (tempo real, exige porta/proxy WebSocket no Traefik). Avaliar trade-off de
      complexidade vs. requisito — RF15 não exige explicitamente tempo real.
- [ ] 2. Confirmar que o Traefik na VPS suporta upgrade WebSocket caso a opção (b) seja escolhida.

### Backend
- [ ] 3. `POST /api/chat/tickets` — abrir ticket de atendimento (aluno autenticado, `req.usuario.sub`).
- [ ] 4. `GET /api/chat/tickets` — listar tickets do aluno (ou todos, se papel NAP/coordenador — RBAC A4).
- [ ] 5. `GET /api/chat/tickets/:id/mensagens` — histórico (anti-IDOR: só dono do ticket ou NAP).
- [ ] 6. `POST /api/chat/tickets/:id/mensagens` — enviar mensagem (persistir em `chat_mensagem`).
- [ ] 7. (Opção b) Canal Socket.io com sala por ticket e autenticação via JWT do cookie.

### Frontend
- [ ] 8. Tela `/dashboard/chat-nap` com lista de tickets + thread de mensagens.
- [ ] 9. Item de menu próprio + estado de "não lidas" (sinergia com Notificações B5/RF10).
- [ ] 10. Visão do NAP (papel) para responder tickets — gated por `RoleRoute`.

### Seed + Encerramento
- [ ] 11. Estender `seed-prod.sql` com 1 ticket de demonstração da persona + resposta do NAP (idempotente).
- [ ] 12. Aplicar seed em produção via túnel SSH; validar `source: db` nos endpoints de chat.
- [ ] 13. Build + `npm test` verde; bump v1.17.0 (3× `package.json`), `CHANGELOG.md`, `README.md`, badge.
- [ ] 14. Commits atômicos pt-BR → push → `node scripts/deploy.mjs` → `/version` = 1.17.0.
- [ ] 15. Validação visual via Playwright MCP (estação): abrir ticket, trocar mensagem, ver persistência.

## Riscos e Cuidados

- **Socket.io adiciona superfície de complexidade** (proxy WebSocket, autenticação no handshake). Se o
  prazo apertar, a opção (a) polling entrega o requisito com menos risco.
- Mensagens de chat são **dados sensíveis** (saúde mental) — aplicar os mesmos cuidados LGPD do D7
  (consentimento, escopo estrito anti-IDOR, sem vazamento entre alunos).
- Rede de segurança de crise: replicar o gatilho NAP/CVV 188 do chatbot caso a mensagem indique risco.
- Tudo na VPS — nenhum serviço de mensageria externo.

## Critério de Conclusão

Aluno abre ticket e troca mensagens com o NAP com persistência verificada em produção (`source: db`),
visão do NAP responde via papel (RBAC), `/version` = **1.17.0** e B3/RF15 marcado ✅ — fechando o
**último requisito funcional** do projeto.
