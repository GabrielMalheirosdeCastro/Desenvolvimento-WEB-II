**Contexto:** Com o Bloco B praticamente fechado (resta só B3/RF15), o próximo passo de menor
risco antes da entrega final é **endurecer a aplicação para "produção de verdade"**: formalizar
uma suíte de testes automatizada e cobrir requisitos não funcionais de segurança. Esta versão
**não entrega RF novo** — é uma versão de qualidade/infra, com foco em **zero quebra** (mudanças
aditivas).

## Objetivo

Entregar, na **v1.13.0**, uma base de qualidade verificável:
1. **Endurecimento de segurança (D1 / RNF03):** headers HTTP de segurança e rate limiting nas
   rotas sensíveis, sem alterar o comportamento funcional existente.
2. **Suíte de testes formal (E1):** consolidar os scripts core (`test-auth-core`, `test-chatbot-core`)
   sob um runner único com `npm test`, permitindo execução padronizada e futura integração em CI.
3. **Testes E2E na estação (E3 / E4):** configurar Playwright com 1–2 specs cobrindo a tela de login
   (4 metadados obrigatórios + badge de versão) e um smoke das telas novas da v1.12.0
   (notificações, eventos, perfil/ranking). **Rodam apenas na estação Windows** — a VPS é headless.
4. **Integração ao CI (E5):** disparar `npm test` no workflow **antes** do deploy, bloqueando
   publicação se os testes core falharem.

## Riscos e Cuidados

- **CSP do helmet pode bloquear a SPA** se mal configurada (assets Vite, inline). Mitigação: testar
  o carregamento local após ativar e ajustar `directives` antes do deploy. Em caso de dúvida,
  começar com CSP em modo report-only.
- **Rate limit atrás do Traefik:** o IP real chega via `X-Forwarded-For`. É necessário configurar
  `app.set('trust proxy', 1)` para o rate-limit contar o IP correto e não o do proxy.
- **Playwright na VPS:** proibido. Os specs E2E rodam **só na estação** (Seção 2.5 das instruções);
  o CI executa apenas os testes core headless.
- **Não migrar tudo para Vitest agora:** manter os scripts core como estão reduz risco; a migração
  formal para Vitest (E1 completo + E2 supertest) pode ser uma v1.13.x ou v1.14.0 dedicada.
