## Sequência recomendada (fatiamento opcional antes do MAJOR)

Para preservar o ritmo de commits atômicos e não acumular um MAJOR gigante, sugere-se executar as
frentes nesta ordem, podendo cada uma virar uma sub-release antes do salto final:

1. **D2 (acessibilidade AA)** — maior impacto direto na banca; pode sair como **v1.31.0** se gerar UI.
2. **E3 (E2E completo)** — só testes/CI, **sem bump de app** (ou PATCH se ajustar config).
3. **D4 + D6 (operação)** — infra na VPS, **sem bump da SPA**.
4. **Bloco G (documentação)** — G2 pode ser incremental; G1/G3/G4 concentrados no fechamento.
5. **Salto v2.0.0** — só quando 1–4 estiverem fechados; o bump MAJOR é o último commit.

> O salto para **2.0.0** não deve ser antecipado com pendências abertas: ele **sela** o backlog.
